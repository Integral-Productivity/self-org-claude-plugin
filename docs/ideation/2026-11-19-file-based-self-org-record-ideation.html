Ideation: a file-based org record for self-org

Focus: Make the plugin also work for people who do not want GlassFrog as their core self-organization system and prefer a file-based record. GlassFrog support keeps working.

Grounding Context

Codebase Context

  • Plugin v1.7.2 (main ffc39ff): 6 skills, 14 commands, 4 agents, 1 SessionStart hook. GlassFrog is reached only through the bundled MCP key glassfrog-extended.
  • Coupling: 50 files in skills, commands, agents and hooks cite glassfrog_* tool names directly. Most cited: create_tension (32), list_roles (31), get_role (29), get_me (25).
  • ADR-0005 names GlassFrog "the first connector behind a governance-data seam" but does not prescribe the interface. Its revisit trigger is "a second backend". It warns the seam erodes if tool calls leak into practice logic. The 50-file count shows that this erosion has happened.
  • STRATEGY.md "Not working on": "Building our own governance record-keeping system — we connect to existing ones (GlassFrog today) through a connector seam, not replace them." A file record needs a decision against this line.
  • Without GlassFrog, skills degrade to "working from what you've shared": no persistence. The ai-governance skill refuses governance-aware patterns outright.
  • evals/stub/glassfrog_stub.py is a 368-line stdio MCP server that computes reads from a synthetic org graph and logs writes. It reproduces live API defects on purpose.
  • Issue #340 brings a second tool vocabulary (GlassFrog's official MCP, camelCase, no tension reads).
  • ADR-0017: no live-org data in this public repo. ADR-0025: the plugin drafts and circulates proposals but never originates or objects.

External context

  • No documented git-and-markdown Holacracy record setup was found, and no open data standard for roles and circles. This is open ground. (Web search at snippet level; not verified against primary pages.)
  • Validation precedent: an Obsidian MCP server validates frontmatter against per-vault JSON Schema. Most vault MCP servers are generic file CRUD with no shape enforcement.
  • Analogies with structural fit: law kept in git (the DC Code accepted a pull request), plain-text accounting (beancount rejects books that do not balance).
  • Risks named: same-clause merge conflicts, format drift, and legitimacy (the Constitution allows governance change only through the governance process).

Topic Axes

  1. Record shape: what the record looks like on disk.
  2. Access path: how skills and commands reach the record.
  3. Legitimacy and write safety: who may change what, and how.
  4. Adoption and coexistence: first run, migration, and running beside GlassFrog.
  5. Verification: keeping two backends honest.

1. Decide that the file record is an open, user-owned format

Adoption and coexistenceConfidence 85%Complexity Low
Description
Write an ADR that amends ADR-0005 and STRATEGY.md. It says the file record is an open, published format that the user owns in their own folder or repository, and the plugin connects to it the way it connects to GlassFrog. The plugin does not host, sync, or own the record. Publish the format as a small spec with JSON Schema, so other tools (a Holaspirit exporter, a hand-kept repo) can target it, the way genealogy apps share the GEDCOM format.
Axis
Adoption and coexistence
Basis
direct: "Building our own governance record-keeping system — we connect to existing ones (GlassFrog today) through a connector seam, not replace them." (STRATEGY.md "Not working on"). external: no open roles-and-circles data standard was found in web research.
Rationale
Every other idea here contradicts a standing strategy line until this decision exists. The reframe keeps the line's intent (do not compete with record systems) while opening a file option. It is a prerequisite, and it is cheap.
Downsides
A published format creates a compatibility promise. A spec written before a working backend may need revision; mark it version 0 until idea 3 runs against it.

2. Make the seam real: a small governance-data verb contract

Access pathConfidence 75%Complexity High
Description
Define a closed list of about 15 verbs that every backend must answer, such as resolve_actor, list_roles, get_role_context, list_tensions and create_tension. Each backend declares which verbs it supports, like a language server declares its capabilities. Skills cite verbs, and degrade per missing capability ("this backend has no tension reads") instead of per vendor ("GlassFrog is not connected"). A lint check holds each backend profile to the verb list.
Axis
Access path
Basis
direct: ADR-0005 does "not prescribe the connector interface's exact signatures" and warns that "GlassFrog-specific calls must be kept behind the governance-data boundary ... or the seam erodes." 50 files now cite tool names. direct: #340 brings a second, camelCase vocabulary. external: Language Server Protocol capability negotiation.
Rationale
One change pays three times: the file backend, the official GlassFrog MCP (#340), and any later backend each become a profile instead of a 50-file edit.
Downsides
The largest edit in the set: 50 prompt files change, and evals must re-baseline. Designing the verbs without a second working backend risks a GlassFrog-shaped contract. Mitigation: design the verbs and build idea 3 together, and treat the first version as provisional.
Confidence
75%
Complexity
High

3. A typed, schema-validating file server built from the eval stub's design

Record shapeConfidence 65%Complexity Medium
Description
Ship a small stdio MCP server, under its own key (for example self-org-files), that reads and writes a folder of markdown files with YAML frontmatter: one file per circle and role, and folders for tensions, projects and actions. It exposes typed tools (not raw file CRUD) and validates every write against JSON Schema files kept in the record's own .self-org/ folder. Reuse the eval stub's architecture (computed reads, a write log), but not its deliberate GlassFrog defects.
Axis
Record shape
Basis
direct: the stub is "A stdio MCP server that serves one synthetic GlassFrog fixture" and "Every response is derived from the fixture's org graph at call time" (evals/stub/glassfrog_stub.py). external: an Obsidian MCP server validates frontmatter against per-vault schemas; most vault servers do not enforce shape.
Rationale
Typed tools keep file layout out of 14 commands, and schema validation replaces the checks GlassFrog does server-side. A working second backend also gives idea 2 real evidence to design against.
Downsides
The stub is not a drop-in: it does not persist, it mints synthetic IDs, and it ships defects on purpose. Persistence is new work. A second server key also touches the tool inventory (evals/glassfrog-tools.tsv), the coach agent's server-prefix list, and MCP_SERVER_NAME in the eval runner. Serving files under glassfrog_* names to skip idea 2 was considered and cut (see the Rejection Summary).
Confidence
65%
Complexity
Medium

4. Legitimacy stack: merge is adoption, checked by a governance validator

Legitimacy and write safetyConfidence 70%Complexity Medium
Description
Split the record into governance (circles, roles, accountabilities, domains, policies) and operations (tensions, projects, actions, checklists, metrics). Operational writes go straight to files after the usual per-item confirmation. The plugin cannot write governance files through its tools, the same limit GlassFrog's API has. Governance changes arrive only as a proposal file or branch; a human (the Secretary) merges it, and the merge is the adoption act. A validator, like fsck for the org or beancount's balance check, rejects invalid states before the merge: a role with no purpose, a domain held by two roles, a policy outside a controlled domain. It exits with an error on an unreadable record, never "clean".
Axis
Legitimacy and write safety
Basis
direct: "The plugin never originates a proposal." (docs/adr/0025). direct: "Read-only governance: Roles, circles, accountabilities, domains, and policies cannot be created, modified, or deleted via API." (skills/self-org-ai-governance/SKILL.md). reasoned: a freely writable governance file bypasses the governance process; making merge the adoption act puts a named human act back in. external: the DC Code accepted a public pull request; beancount rejects unbalanced books.
Rationale
It makes legitimacy a property of the storage design, not a rule each command must remember, and it gives file users something GlassFrog's API does not: a diffable governance history.
Downsides
Git cannot stop a person who edits files by hand; the validator and CI catch shape errors, not illegitimate intent. The validator's invariants must cite Constitution sections (lint check 14) and avoid contested readings. It assumes the record is a git repository; a plain folder gets the validator but not the merge gate.
Confidence
70%
Complexity
Medium

5. GlassFrog-to-files export with a provenance crosswalk

Adoption and coexistenceConfidence 70%Complexity Medium
Description
A command reads a live GlassFrog org and writes it into the file format, in a folder the user names. Each record carries source: glassfrog, source_id and retrieved_at, as library catalogs keep the source record's control number. Later runs show a per-item drift list and never overwrite in bulk. The command refuses to write inside this plugin's checkout or any public repository.
Axis
Adoption and coexistence
Basis
direct: ADR-0005's revisit trigger is "a second backend (e.g., Holaspirit), HolacracyOne's official MCP". direct: ADR-0017 keeps org data out of this public repo. reasoned: the sibling glassfrog-config repo already refuses to sync over drift and stamps a synced field; the same pattern fits here.
Rationale
It makes the choice reversible. A GlassFrog org can try file mode for a month and go back; a file-first org can move into GlassFrog later. It also gives GlassFrog users an offline, diffable snapshot.
Downsides
It inherits API defects on read (for example, list_subrole_tensions returns direct children only), so the export must walk circle by circle. Writing back to GlassFrog is a separate, harder step and is out of scope at first.
Confidence
70%
Complexity
Medium

6. One conformance suite for every backend

VerificationConfidence 60%Complexity Medium
Description
Render each synthetic scenario in evals/scenarios/ both as a GlassFrog fixture and as a file record, run the same eval cases against each backend, and require the same write log. Move known GlassFrog defects out of the stub's code into a per-backend expectations file, as the browser vendors do for Web Platform Tests, so the file backend does not inherit them by accident.
Axis
Verification
Basis
direct: the stub runs from GLASSFROG_STUB_FIXTURE and GLASSFROG_STUB_WRITE_LOG, and "One write is deliberately NOT accommodating: update_tension rejects" meeting_type (evals/stub/glassfrog_stub.py). external: Web Platform Tests per-engine expectation files.
Rationale
It turns "GlassFrog support keeps working" and "file support keeps working" into checked claims, and it bounds the maintenance cost of two backends.
Downsides
It only pays once idea 3 exists. The identical-write-log assertion is untested and may need a per-backend normalizer for IDs.
Confidence
60%
Complexity
Medium

7. Ground file-mode sessions: the SessionStart hook detects a record

Access pathConfidence 80%Complexity Low
Description
Extend the SessionStart hook so it emits the role-grounding directive when it finds a file record (a .self-org/ folder or a SELF_ORG_RECORD path), not only when an authenticated GlassFrog connector is detected.
Axis
Access path
Basis
direct: the hook's description says the directive is "emitted ONLY when an authenticated GlassFrog connector is detected" (hooks/hooks.json).
Rationale
Without it, file users silently lose the plugin's central measured behavior, and the grounding readout counts them as misses. It is small, and it is easy to forget.
Downsides
Small on its own; it belongs inside the idea-3 work, not as a separate project. The readout scripts must learn the new trigger too.
Confidence
80%
Complexity
Low
